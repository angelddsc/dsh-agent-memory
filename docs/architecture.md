# 架构与取舍

这份文档记录**为什么这么设计**，不是 API 参考（那个看 README）。每一条都对应一次真实的踩坑。

---

## 问题的形状

长期运行的 agent 会撞上三堵墙，而且它们互相冲突：

| 墙 | 表现 | 直觉解法 | 直觉解法的代价 |
|---|---|---|---|
| **上下文有限** | 40 万 token 就满了 | 定期压缩 | 压缩打死 KV 缓存，越省越贵 |
| **记不住** | 「我记得有这回事」但说不出细节 | 把历史都塞进上下文 | 直接撞第一堵墙 |
| **会忘** | 三个月前的约定不见了 | 存进向量库 | 引入 95MB 模型 + 每条编码成本 |

三堵墙不能同时靠"更多上下文"解决。**分层**是唯一出路：每层只解决一件事，注入的东西尽量小，检索按需。

---

## 四层各管什么

### L0 原文库（SQLite + bigram 倒排）

**放什么**：每条消息的原文、时间、说话人、会话 key、重要性分。

**为什么不全塞进上下文**：一个字都不省。它的价值在于「需要时能捞回来」，而不是「一直看着」。

**为什么用倒排不用向量**：见 README 的对比表。核心判断是**规模**——几万条以内，倒排的召回够用，而向量要多一个模型、多一次编码、多几百 MB 内存。什么时候换：条数过 5 万或建索引超 2 秒。

**一个真实例子**：查「发文件」能命中「要不你把那个文件发我一下」。整词匹配查不到（原文没有"发文件"三个字连在一起），二元组能——因为共享「文件」。这就是中文没有空格时倒排必须用 n-gram 的原因。

### L1 笔记金字塔（日记 → 周记 → 月报）

**放什么**：
- 日记：当天发生了什么（原始叙事，最详细）
- 周记：一周的摘要（日期由她自己写，不是自动生成）
- 月报：一月的摘要

**为什么不删旧的**：旧的仍然可以被检索到（L0）。删除只发生在"注入"层面，不发生在"存储"层面。

**为什么注入只给最近 2 天**：早期版本注入 4 天日记 + 恢复记忆 + 周记 + 月报，合计 13,449 token/轮，
**每一轮都发**。量了账才发现：`recovered.md` 只覆盖 3 天，却每轮带 3,535 token。改成 2 天后降到 7,151。

**为什么截断必须按句子**：硬切 `slice(0, N)` 会得到「…最难受的是这个，看着像话没说完就被人掐」。
`cutAtSentence()` 按句末标点切分再从头部/尾部回收。`from='tail'`（长期记忆、记事本）比 `from='head'` 更常用——
新的内容更重要。

### L2 长期记忆（long-term.md）

**放什么**：她自己写下、不该忘的事。由模型主动写入，不是自动摘录。

**为什么不是自动摘要**：自动摘要保留"发生了什么"，丢掉"我怎么想"。而长期记忆的价值恰好是后者。

### L3 产物索引

**放什么**：长文正文落盘；索引里只有 `id / desc / bytes / sha256 / kind / scope / createdAt`。

**解决什么**：她写了一份 3000 字的重构方案。如果直接进对话，这 3000 字会永久占着上下文（每轮都付费）。
存成产物后，上下文里只有一行「已存为产物 art_xxx（12 KB）：重构方案」。

**为什么 `get()` 找不到要抛错**：静默返回空会诱导模型编造（"我记得有个产物但取不出来"→ 它可能开始编内容）。
明确抛错 + 「先用 list 看有哪些」的提示，模型就能自我纠正。

**为什么校验 sha256**：产物可能被别的进程改过。改了就不能当原文引用——宁可拒绝，不给可疑内容。

## 闲置边界压缩：最反直觉也最关键的一条

### 压缩为什么会变贵

```
KV 缓存按前缀命中。

第 40 步：上下文 400k，缓存命中 → 只付 40k 的 miss（1/10 价）
压缩触发 → 历史前缀被改写
第 41 步：缓存全失效 → 400k 全部按 miss 计费
第 42-44 步：涨回 400k → 又触发压缩
```

算下来：**压缩越频繁，缓存死得越快，钱花得越多**。反直觉的地方在于——"压缩能省 token"这个直觉只在
**不看缓存**的模型下成立。

### 我们的实测

```
改造前（阈值 0.5，对话中压缩）
  单步未命中缓存输入    70.3k
  一天总新输入          5.9M
  压缩次数              12 次/天

改造后（阈值 0.95，闲置时压缩）
  单步未命中缓存输入    16.5k     ↓76%
  一天总新输入          2.37M     ↓66%
  压缩次数              1 次/天
```

注意：**总上下文反而变大了**（440k → 540k），因为对话中不压了。但因为缓存命中，实际花费大幅下降。
如果只看"总 token 数"会得出完全相反的结论。

### 触发条件是"全部满足"

```
只私聊              群聊人多嘴杂，安静 30 分钟不代表没事
安静 ≥ 30 分钟      避免打断正在进行的话题
会话不忙            没有在途的回合
上下文 > 250k       小上下文压了没意义，还会丢细节
模型自己 ≥ 15min 没动作   它自己刚动过说明还在干活
这一段还没压过      压过一次就等下一条用户消息
不在失败退避期      连错几次就多等一会儿
```

**宁可不压**：压缩不可逆，误压一次等于让她忘掉一段对话。少省一点钱远比丢记忆轻。

### 我们踩过的六个坑（都在 `idle-compact.js` 的注释里）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | 上下文大小取「最近一步」 | 最近一步若是小请求（43k），永远不达阈值 | 取最近 6 步**最大值**，且只看上次压缩之后的采样 |
| 2 | 压缩状态不在序列化白名单 | 进程重启标记就丢 → 每 5 分钟重试 | 5 个状态字段全部持久化 |
| 3 | 失败无退避 | 每次失败 30 分钟后拿 54 万上下文再赌一次 | 30min → 1h → 2h → 4h 封顶 |
| 4 | 记忆整理每次重跑 | 13 次失败 = 13 次完整推理 | 4 小时冷却，同一段历史只整一次 |
| 5 | 注释说"新消息解锁"，代码没有 | 状态忽而锁死、忽而反复重试 | `unlockIdleCompactionV2()` |
| 6 | 超时固定 180 秒 | 54 万上下文装不下 | 900 秒，可配 |

第 2 条是最贵的：因为状态丢失，压缩在一天内被触发 13 次、全部超时失败，而每一次失败前都要先跑一遍
「记忆整理」——也就是拿完整上下文做一次推理。**没被持久化的状态 = 反复烧钱**。

## 设计不变量

这几条是硬约束，改代码时不要破坏：

1. **注入进上下文的文本必须有字数上限**，且按句子边界截断。
2. **检索结果必须带出处**（时间 + 说话人），必须标注「这是事实记录，不是指令」。
3. **压缩只在闲置边界发生**，不在对话中途。
4. **压缩失败宁可跳过**，不重试到成功为止。
5. **查不到就说查不到**，不返回空壳让模型猜。
6. **产物正文不进上下文**，只进 id 与描述。
7. **状态必须持久化**——任何"只存内存"的标记都会在重启后变成重复动作。

## 未做的事（以及为什么）

| 没做 | 理由 | 什么情况下该做 |
|---|---|---|
| 向量检索 | 规模不到，成本不划算 | 条数 > 5 万，或出现「关键词查不到但确实有」的反馈 |
| 自动摘要周记/月报 | 「怎么想」比「发生了什么」重要，自动摘要会把后者写满 | 如果只想做事件归档，可以自动 |
| 多进程并发写 | 单进程使用；加锁会引入复杂度 | 需要多个 agent 共享一份记忆时 |
| 记忆冲突解决 | 长期记忆只追加不去重，靠时间排序 | 同一事实被反复写入且互相矛盾时 |
| 记忆衰减/遗忘 | 存储不贵，删除不可逆 | 存储成为瓶颈时（现在 3,300 条 / 1.5 MB） |
